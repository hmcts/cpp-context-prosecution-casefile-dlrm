## T2 — BC-08 payload boundary (AC5)

**File:**
`pcfdlrm-event/pcfdlrm-event-processor/src/test/java/uk/gov/moj/cpp/pcfdlrm/event/processor/MigratedCaseReceivedProcessorTest.java`
(existing test, `shouldConvertAndSendInitiateCourtProceedings`, lines 90–94 — modify, don't duplicate)

- **Current shape:** `courtProceedingsInitiated` (and the paths that carry `listedStartDateTime`) are
  in the `WholePayloadMatcher` exclusion list, skipped entirely from the whole-payload comparison.
- **New shape:** remove those two paths from the blanket exclusion list; add a **separate, explicit**
  assertion straight after the `matchesWholePayload(...)` check:
  ```
  assertThat(actualPayload, matchesJsonPath(
      "initiateCourtProceedings.prosecutionCases[0].defendants[0].courtProceedingsInitiated",
      endsWith("TBC (J17 run — the region-zone suffix, e.g. \"[UTC]\")")));
  ```
  (exact matcher/library call TBC — use whatever JSON-path assertion helper this test class already
  imports; do not add a new dependency for one assertion).
- **Why not a new test:** this is the one place in the repo that already builds and compares the
  **whole** outbound `initiateCourtProceedings` payload — the literal boundary to
  `cpp-context-prosecution-casefile`. Narrowing an existing exclusion satisfies AC5 without a second,
  parallel payload-construction fixture.
- **Sanity check before committing (not a committed test):** temporarily mutate the pattern to
  something that should fail, confirm the test goes red, then restore. This is due diligence, not a
  permanent mutation test — do not commit a broken-on-purpose variant.

## T3 — BC-11 null-guard parity

**File (new):**
`pcfdlrm-event/pcfdlrm-event-processor/src/test/java/uk/gov/moj/cpp/pcfdlrm/event/processor/utils/JsonObjectsNullGuardParityTest.java`

```
class JsonObjectsNullGuardParityTest {

    @Test
    // BC-11 (corrected 2026-08-26): the original "JSON-P provider collision" hypothesis was refuted
    // by a real J17/J25 run on cpp-context-notification-notify. The framework helper's own
    // null-guard throws identically on both runtimes — this pins that guard, not provider
    // resolution. See 01-requirements.md FR9 (revised) and 00-input-brief.md's re-weighting.
    void shouldThrowNpeWhenNullValueAddedToObjectBuilder() {
        final JsonObjectBuilder builder = JsonObjects.createObjectBuilder();

        final NullPointerException thrown = assertThrows(NullPointerException.class,
                () -> builder.add("aKey", (String) null));

        assertThat(thrown.getMessage(), is("TBC (J17 run)"));
    }
}
```

- **Why this shape:** exercises `uk.gov.justice.services.messaging.JsonObjects` **directly** — the
  same helper `MetadataHelper`/`EnvelopeHelper`/`MaterialEventProcessor` call — rather than routing
  through any one caller's business logic, mirroring how the corrected guide's own reference test
  worked. One method is sufficient: this is a parity pin on shared framework behaviour, not a
  per-caller test (`02-design.md` §B).

## T4 — BC-20 rule-count gap

**File (new):**
`pcfdlrm-command/pcfdlrm-command-api/src/test/java/uk/gov/moj/cpp/pcfdlrm/command/api/accesscontrol/CommandApiKnowledgeBaseRuleCountTest.java`

```
class CommandApiKnowledgeBaseRuleCountTest {

    @Test
    // BC-20: a Drools test harness silently loading 0 rules lets deny-tests pass vacuously. This
    // repo's kmodule.xml has exactly one kbase (COMMAND_API) — no multi-kbase 0-rule trap to guard
    // against (contrast cpp-context-system-doc-generator's QUERY_API kbase).
    void shouldLoadNonZeroRuleCountForCommandApiKbase() {
        final KieBase kieBase = KieServices.get().getKieClasspathContainer().getKieBase("COMMAND_API");

        final long ruleCount = kieBase.getKiePackages().stream()
                .mapToLong(kiePackage -> kiePackage.getRules().size())
                .sum();

        assertTrue(ruleCount > 0, "Expected COMMAND_API kbase to load at least one rule");
    }
}
```

- **Blocking pre-work — do this before writing the test, not after:** confirm the exact accessor
  chain (`KieServices.get().getKieClasspathContainer().getKieBase(name)`, or whatever this repo's
  actual `access-control-test-utils` version exposes) against that dependency's real API. Per design
  note #4, do **not** copy the investigation report's snippet without checking — the pseudocode above
  is the starting hypothesis from the reference guide's own evidence log, not a verified call.
  `StatelessKieSession` (what `ReceiveMigratedCaseRuleTest` extends via
  `BaseDroolsAccessControlTest("COMMAND_API_SESSION")`) does not expose the `KieBase` directly, which
  is why this needs its own path via `KieServices`, not a shortcut through the existing test's
  session.

**File (new):**
`pcfdlrm-viewstore/pcfdlrm-viewstore-liquibase/src/test/java/uk/gov/moj/cpp/pcfdlrm/viewstore/liquibase/LiquibasePropertiesKeyInventoryTest.java`

```
class LiquibasePropertiesKeyInventoryTest {

    @Test
    // BC-07: Liquibase 4→5 rejects removed properties (hub.mode, searchPath). This pins today's key
    // set — including liquibase.hub.mode, the exact property the corrected guide flags — so its
    // removal in the upgrade story is a deliberate, visible diff against this test, not a silent
    // K8s pre-install failure. Removal itself is the upgrade story's job (FR16); not done here.
    void shouldExposeExactlyTheCurrentSupportedKeySet() throws IOException {
        final Properties properties = new Properties();
        try (InputStream in = getClass().getClassLoader().getResourceAsStream("liquibase.properties")) {
            properties.load(in);
        }

        assertEquals(Set.of("changelogFile", "liquibase.hub.mode", "liquibase.headless"),
                properties.stringPropertyNames());
    }
}
```

- No `TBC` marker needed here — the key set was read directly from the file in Stage 2 and is not
  runtime-dependent.

class GeneratedEventTypeInventoryTest {

    private static final String SCHEMA_DIR = "json/schema";
    private static final String GENERATED_PACKAGE = "uk.gov.moj.cps.prosecution.casefile.dlrm.domain.event";

        final Set<String> expectedTypeNames = schemaFileNames(SCHEMA_DIR).stream()
                .map(GeneratedEventTypeInventoryTest::schemaIdToTypeName) // TBC (J17 run) — confirm

                                                                            // the plugin's own contract

                .collect(toSet());

        for (String typeName : expectedTypeNames) {
            assertDoesNotThrow(() -> Class.forName(GENERATED_PACKAGE + "." + typeName),
